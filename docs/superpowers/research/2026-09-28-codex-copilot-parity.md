## Probe results (2026-09-28, short real sessions, "Reply with the single word ok.")

Everything below was observed, not read. The probe hook appended its stdin, its parent chain
and the event name to a scratch file.

**Copilot CLI 0.0.369 (the version installed via Homebrew, December 2025).**
- Repo hooks in `.github/hooks/*.json` fire without any trust step, but the payload has **no
  session id**: `{timestamp, cwd, prompt}` / `{…, source: "new", initialPrompt}` /
  `{…, reason: "complete"}`. No `agentStop` fired under `-p`. There is no `--session-id` flag.
- Sessions are flat files `~/.copilot/session-state/<id>.jsonl`; `session.start` has no cwd.
  `assistant.turn_start` / `assistant.turn_end` are written.
- Conclusion: 0.0.x cannot be tied to a session from a hook. The app requires Copilot ≥ 1.0.

**Copilot CLI 1.0.89 (`npx @github/copilot@1.0.89`, isolated `COPILOT_HOME`).**
- User-level hooks in `$COPILOT_HOME/hooks/*.json` fire. camelCase events observed:
  `userPromptSubmitted`, `sessionStart` (`source`, `initialPrompt`), `agentStop`
  (`transcriptPath`, `stopReason: "end_turn"`, `stop_hook_active`), `sessionEnd`
  (`reason`). Every payload has `sessionId`, `timestamp`, `cwd`.
- The hook's parent process is the native `copilot` binary
  (`…/@github/copilot-darwin-arm64/copilot`), so the parent pid is the CLI's pid.
- Repo hooks in `.github/hooks/probe.json` did **not** fire under `-p`, with or without mixed
  event-name styles. Cause not established (folder trust is the likely one).
- Session folder `session-state/<id>/` has `events.jsonl` and `workspace.yaml` with `id`,
  `cwd`, `git_root`, `branch`, `name`, `created_at`, `updated_at`. `session.start.data.context`
  has `cwd`, `gitRoot`, `branch`. `-p` prints `Resume copilot --resume=<id>` at the end.

**Codex CLI 0.158.0.**
- Repo hooks in `<repo>/.codex/hooks.json` in an untrusted directory were **silently not
  run** by `codex exec`. The only non-interactive way past trust is
  `--dangerously-bypass-hook-trust`, which the app will not use. `features.hooks` is on.
- The rollout of that run has `session_meta` (`session_id`, `id`, `timestamp`, `cwd`, …),
  `event_msg` `task_started` … `task_complete`, `turn_context` (`cwd`, `approval_policy`, …)
  and `event_msg` `token_count`. busy/idle can therefore be read from the rollout alone.
- Codex loads user skills from `~/.agents/skills` (its log reported a skill there with a
  missing frontmatter).
- Not observed: Codex hook payloads, `PermissionRequest`, or how trust is granted
  interactively. Those stay assumed.

**The session id is in every tool's shell environment** (observed with `env` run by each tool):
- Codex 0.158.0: `CODEX_THREAD_ID` and `CODEX_SESSION_ID` (same value), plus `CODEX_VERSION`.
- Copilot 1.0.89: `COPILOT_AGENT_SESSION_ID`, plus `COPILOT_CLI=1`, `COPILOT_CLI_BINARY_VERSION`.
- Claude Code 2.1.284: `CLAUDE_CODE_SESSION_ID`, plus `CLAUDECODE=1`.
- These variables are inherited by nested tools. A Copilot launched from inside Claude Code saw
  `CLAUDE_CODE_SESSION_ID` set to a value that matched neither session. So a skill must first
  find which tool is its nearest ancestor process, then read that tool's variable only.
